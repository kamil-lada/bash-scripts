# Jenkins rebuild — Docker Compose controller + SSH workers (handoff, decided 2026-11-18)

Planning session 2026-11-17/18. Scripts written and tested in the build session 2026-11-18 (see "Build session results" at the end). Supersedes the earlier plans: JCasC + Job DSL + plugins.txt, and ephemeral Terraform LXC agents (both dropped).

## Goal

Rebuild Jenkins from scratch with Compose + `.env` + scripts. Scripts ask questions at start. No GUI setup except creating jobs. No JCasC, no seed job. Each job is created by hand as "Pipeline script from SCM" pointing at its own git config.

## Verified facts (source in brackets)

- Jenkins 2.555.1+ requires Java 21 or 25 on controller **and** agents. Docs (upgrade-java-to-25): agents need only the minimum supported Java. Maintainer (community t/36810): if the controller runs Java 25, agents must run 25. → jdk25 image + Debian 13 `openjdk-25-jre-headless` on workers (same major). [[jenkins.io/doc/upgrade-guide/2.555](http://jenkins.io/doc/upgrade-guide/2.555); [community.jenkins.io](http://community.jenkins.io) t/36810; jenkins.io/doc/book/platform-information/upgrade-java-to-25]
- SSH Build Agents compares the MD5 of remoting.jar on every launch and copies it if different, so it always matches the controller. [JENKINS-56147; JENKINS-70214 log]
- Host key strategies: Known hosts file / Manually provided / Manually trusted / Non verifying. With Manually trusted, the key received on the initial connection is trusted automatically (unless manual verification is required), and a changed key afterwards needs manual approval. [CloudBees KB 115000073552; ssh-slaves javadoc verifiers]
- Without retry settings, an offline SSH agent is retried by the retention strategy roughly every 5 min. Configuring retries/wait/timeout gives faster automatic reconnects. [JENKINS-52613 comment]
- Groovy hook scripts in `$JENKINS_HOME/init.groovy.d/*.groovy` run at the end of Jenkins initialization, in lexical order, with access to Jenkins and all plugins, **on every start**. [[jenkins.io/doc/book/managing/groovy-hook-scripts](http://jenkins.io/doc/book/managing/groovy-hook-scripts); GroovyHookScript javadoc]
- `-Djenkins.install.runSetupWizard=false` skips the setup wizard. Common pattern: create the admin user plus `HudsonPrivateSecurityRealm` and `FullControlOnceLoggedInAuthorizationStrategy` (anonymous read off) in an init script, then delete the script. [jenkinsci-users; labex example; docontop]
- `jenkins-plugin-cli --plugin-file … --plugin-download-directory …` can be run inside the stock image. [plugin-installation-manager-tool README]
- The official image runs as UID/GID 1000 and its entrypoint does not do uid/gid mapping, so a bind mount must be chowned to 1000:1000. [[forums.docker.com](http://forums.docker.com) 77242; multiple SO answers]
- Git client plugin defaults to the "Known hosts file" strategy, using `known_hosts` on the **controller and on each agent**. → [github.com](http://github.com) must be in both. [[plugins.jenkins.io/git-client](http://plugins.jenkins.io/git-client); JENKINS-69149]
- A GitHub deploy key can be attached to **one** repository only ("Key already in use"). [[docs.github.com](http://docs.github.com) error-key-already-in-use]
- Running builds on the built-in node gives them the controller's file access. Recommended: 0 executors. [[jenkins.io/doc/book/security/controller-isolation](http://jenkins.io/doc/book/security/controller-isolation)]
- Credentials are encrypted with `secrets/master.key` + `secrets/hudson.util.Secret` and are not portable between instances. [SO 38465270, 35603191]
- Global config is spread over several XML files in `JENKINS_HOME`, not only `config.xml` (e.g. the URL is in `jenkins.model.JenkinsLocationConfiguration.xml`).
- Admin can run Groovy remotely via POST `/scriptText`. A CSRF crumb is needed for password auth. An API token needs no crumb (since 2.96). [[jenkins.io/doc/book/managing/script-console](http://jenkins.io/doc/book/managing/script-console); JCasC reload docs]

## S1 — [`jenkins-controller.sh`](http://jenkins-controller.sh) (run on the Docker host)

The start banner prints what the script does, the three modes, the overall order (controller → worker any time later → Caddy/NPM route → create jobs), and that the worker script can be run before or after.

**Mode question first:**

1. Controller only (no workers): built-in executors asked, default 2. One-line warning about builds on the built-in node.
2. Controller + worker(s): built-in 0. For each worker: name, IP, executors (default 3), labels, agent folder (default `/home/jenkins/agent-<controller-name>`).
3. Add worker to an existing controller: reads `<stack>/.env`. Asks worker details and the admin password (not stored). Creates the node on the running Jenkins via `/scriptText` (same node Groovy as first boot, no restart). If built-in executors > 0, offers to set them to 0. Uses the existing agent credential, no new key. Prints the worker command.

**Questions (modes 1 and 2):** stack path, controller name, bind IP:port (default 10.0.20.10:8080), Jenkins HTTPS URL, admin user + password, timezone (default Europe/Warsaw), image tag (pinned LTS-jdk21), extra plugins, GitHub live check y/N.

**What it does (modes 1 and 2), in order:**

1. Creates `<stack>/` with `compose.yaml`, `.env`, `plugins.txt`, `jenkins_home/` (chown 1000:1000) and `keys/`. Refuses to run on a non-empty `jenkins_home`.
2. Downloads plugins into `jenkins_home/plugins` with `jenkins-plugin-cli` (one-off `docker compose run`). Baseline list: ssh-slaves, git, workflow-aggregator, credentials-binding, plus extras and the settings from the dump (S3).
3. Generates key pairs: `agent_ed25519` (mode 2; in mode 1 only if the user wants it for later) and `github_ed25519`.
4. Adds [github.com](http://github.com) host keys to `jenkins_home/.ssh/known_hosts` (verify fingerprints against GitHub's published ones).
5. Writes first-boot Groovy into `jenkins_home/init.groovy.d/`, idempotent, values from a temp file that is deleted afterwards: security realm + admin, authorization (logged-in full control, anonymous read off), URL, built-in executors, timezone (via `JAVA_OPTS -Duser.timezone`), credentials (agent key, GitHub key with username `git`), git host-key strategy = Known hosts file, nodes (DumbSlave, SSHLauncher: host, port 22, credential, Java path `/usr/lib/jvm/java-21-openjdk-amd64/bin/java`, ManuallyTrustedKeyVerificationStrategy(false), retries/wait set; RetentionStrategy.Always; executors; labels; remote FS), settings taken from the dump.
6. `docker compose up -d` and waits until Jenkins is up.
7. Deletes `init.groovy.d/*`, the temp values file, the plain-text admin password and the private keys.
8. Prints: the GitHub public key (paste as a read-only deploy key), the ready-to-paste worker command per worker (with the public key and agent folder), then the optional GitHub check, the remaining steps (Caddy/NPM route, create jobs) and where the public keys are kept.

`compose.yaml`**:** image tag from `.env`, `JAVA_OPTS` (wizard off, timezone), bind mount `./jenkins_home:/var/jenkins_home`, port bound to the given IP, `restart: unless-stopped`. No port 50000.

## S2 — [`jenkins-worker.sh`](http://jenkins-worker.sh) (run on a fresh Debian 13 LXC/VM)

Usage, printed by S1: `bash [jenkins-worker.sh](http://jenkins-worker.sh) --key '<controller agent pubkey>' --dir <agent folder>`.

- Installs `openjdk-<N>-jre-headless` (`--java N`, default 25, printed by S1), `git`, `openssh-server`. Creates the `jenkins` user if missing and the agent folder if missing.
- Adds the key to `~jenkins/.ssh/authorized_keys` **only if not present** (keys of other controllers stay). Adds [github.com](http://github.com) to `~jenkins/.ssh/known_hosts` only if missing.
- **Safe to re-run** (same or another controller). Never deletes anything.
- Prints a summary: user, folder, Java version, host key fingerprint (informational only, D12).

## S3 — [`jenkins-dump.sh`](http://jenkins-dump.sh) (one-off, run on a temporary instance Adam configured in the GUI)

Output: a folder/tarball for the build session, **not** used by S1 at runtime.

- **Include:** top-level `*.xml` from `JENKINS_HOME` and a pinned plugin list `name:version`.
- **Exclude:** `secrets/`, `secret.key*`, `identity.key.enc`, `credentials.xml`, `users/`, `nodes/`, `jobs/`, `workspace/`, logs.
- The build session reads the dump and turns the settings Adam wants into S1 Groovy and defaults.
- Any `{AQAAAB…}` encrypted values in the dump are not portable. They must become questions or `.env` values.

### What S1 adds beyond the plan

- `-Djenkins.model.Jenkins.slaveAgentPort=-1`: the inbound TCP agent listener is off. It is the initial value only and can still be changed in the GUI.
- `stop_grace_period: 60s` in compose.
- Values are embedded in the first-boot Groovy as base64 (the Groovy file is the temp values file). Private keys are kept in `jenkins_home/.bootstrap/` until cleanup. An EXIT trap removes `.bootstrap/` and `init.groovy.d/*` on every exit, including failures. After a failure: `docker compose down`, wipe `jenkins_home`, re-run.
- The Groovy writes `.bootstrap/done` or `.bootstrap/failed`, so S1 fails fast instead of waiting for the timeout.
- github.com host keys come from `ssh-keyscan`, and each fingerprint is checked against `api.github.com/meta` (S1 and S2).
- The live GitHub check runs before cleanup: S1 waits for Enter after printing the deploy key, then runs `ssh -T` inside the container with the controller's `known_hosts`.
- Mode 3 on a mode-1 controller without an agent key creates the key and credential at that point. Re-running mode 3 skips existing nodes.
- SSH launcher: 10 retries × 15 s, launch timeout 60 s, then `RetentionStrategy.Always` keeps retrying.

### Tests passed

Fresh runs of modes 1, 2 and 3 (3 against both a mode-1 and a mode-2 controller). Refusal on a non-empty `jenkins_home`. S2 re-run changes nothing (file stat checksum). S2 with a second controller's key adds a second line. All settings persist after `docker compose restart`, and `init.groovy.d` is empty. No private keys or admin password on disk (the password included `$ " \` characters). Anonymous gets 403. Agent set up after the controller came online 16 s after sshd started. When the worker was set up 4+ min later (all 10 launcher retries used), the retention strategy started a new launch about 1 min later, and the agent connected 5 s after the worker was ready. ed25519 agent key works with ssh-slaves. Host key was auto-trusted, and its fingerprint matches S2's summary. A pipeline on the worker and "Pipeline script from SCM" on the controller both pass GitHub host-key verification. Without the worker's `known_hosts`, the checkout fails with "Host key verification failed". The dump in container mode and dir mode masks `{AQAAAB…}` values and lists them.

### Java 25 switch (2026-11-19)

Default tag changed to `2.580.2-lts-jdk25`. S1 reads the Java major from the tag suffix (`-jdkNN`, required) and uses it for the node Java path (`/usr/lib/jvm/java-NN-openjdk-amd64/bin/java`) and for the printed worker command (`--java NN`). Mode 3 reads it from `JENKINS_TAG` in `.env`. S2 takes `--java N` (default 25) and installs `openjdk-N-jre-headless`.

Checked impact:

- **Image:** jdk25 and jdk21 have the same WAR, entrypoint, Debian 13 base, uid 1000 and HOME. Only the JDK differs (Temurin 25.0.5). The image is **997 MB vs 712 MB**.
- **Workers:** `openjdk-25-jre-headless` is in Debian 13 main (25.0.3) and trixie-security (25.0.5). No extra repository needed.
- **Agents:** tested with the controller on 25. A Java 25 agent and a Java 21 agent both ran `sh`, stash/unstash, archiveArtifacts, junit and a git checkout over SSH. Workers are still set to the same major, following the maintainer's advice.
- **Logs:** one startup warning from Java 24+: XStream (bundled in the WAR) calls the deprecated `sun.misc.Unsafe::objectFieldOffset`. Harmless now. It becomes a problem only when a future JDK removes it, and Jenkins core has to update XStream before that.
- **GUI:** the "Java 21 end of support" banner is gone. The CSP recommendation remains.
- **Memory:** about 780 MB RSS idle with 2 agents. Not compared against 21.
- **Builds:** the worker JRE runs remoting. Builds that call plain `java` on the worker get 25 if it is the newest one installed (Debian alternatives priority). Builds that need a specific JDK should use a Jenkins tool installation.
- **One worker, two controllers:** both JREs can be installed side by side. Each node's Java path picks its own.
- **Changing the tag later:** if `JENKINS_TAG` in `.env` changes major (e.g. back to jdk21, or to a future jdk), existing nodes keep their old Java path. Update them in the GUI and run S2 with the new `--java` on the workers.
